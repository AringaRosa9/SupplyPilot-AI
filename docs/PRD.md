# SupplyPilot AI 产品需求文档

| 项目 | 内容 |
|---|---|
| 产品名称 | SupplyPilot AI |
| 产品定位 | 全球旅游电商供应链招商与货品决策平台 |
| 文档版本 | v0.1 |
| 当前状态 | Draft |
| MVP 产线 | Hotel、Flight |

## 1. 项目背景

旅游电商的供应链招商通常横跨营销、供应链、商品运营、技术和不同业务产线。活动需求由营销团队发起后，需要被拆解为具体招商任务，再经历供应商协调、商品提交、数据校验、产品评级、人工审核和上架等多个环节。

现有流程往往存在以下问题：

- 招商请求分散在表格、即时通信和邮件中，难以统一追踪。
- 活动要求依赖人工理解和转述，容易遗漏约束条件。
- 不同产线采用不同入池和评级标准，缺少统一的系统承载方式。
- 供给缺口、供应商集中度和库存风险发现较晚。
- 评级结果缺少解释，难以与上架及前台排序形成闭环。
- 活动复盘局限于单次活动，无法长期评估供应商及产线策略。

SupplyPilot AI 将活动招商、货品管理、产品评级、供给分析和智能决策整合到同一条可追踪、可配置、可审计的工作流中。

## 2. 产品定位

SupplyPilot AI 是一个面向旅游电商场景的供应链招商智能平台，覆盖：

```text
招商请求发起 → 商品提交 → 自动筛选 → 产品评级 → 货品池管理
             → 供给洞察 → 招商策略建议 → 活动与产线复盘
```

项目重点不是简单实现一个管理后台，而是展示如何把复杂业务问题转化为：

- 可落地的产品流程
- 可解释的评分模型
- AI Agent 决策能力
- 自动化任务与预警机制
- 可演进的前后端与数据工程方案

第一阶段聚焦 Hotel、Flight 两条产线，同时通过可配置的规则和评分模型预留扩展其他产线的能力。

## 3. 产品目标

### 3.1 业务目标

- 统一管理不同市场、活动和产线的招商请求。
- 将自然语言活动需求转换为可执行的结构化招商条件。
- 自动识别供给缺口，并生成招商优先级和行动建议。
- 根据不同产线规则自动筛选和评级商品。
- 实时追踪商品从招商提交到上架的全生命周期。
- 分析供应商质量、货盘健康度和招商策略效果。
- 将评级结果转化为前台推荐及排序建议。

### 3.2 项目展示目标

通过一个可运行、可演示、可解释的 GitHub 项目，展示候选人的：

- 供应链业务抽象能力
- AI Agent 与工作流设计能力
- 数据分析及评分模型能力
- 全栈工程实现能力
- 跨团队系统方案设计能力

### 3.3 非目标

MVP 不试图替代真实企业内部的供应商、库存、定价或推荐系统，也不直接执行不可逆的业务决策。项目首先验证端到端流程、数据模型、评分解释和智能决策方式。

## 4. 核心用户

| 用户角色 | 主要诉求 |
|---|---|
| 全球营销运营 | 发起活动招商，了解商品准备情况和活动风险 |
| 供应链招商经理 | 接收任务、跟进供应商、补齐供给缺口 |
| 产线负责人 | 查看货盘健康度、招商进度和市场覆盖 |
| 商品运营 | 完成评级审核、商品上架和异常处理 |
| 管理层 | 查看跨产线供给风险和周期性策略复盘 |
| 算法/技术团队 | 配置评分模型、业务规则和自动化策略 |

## 5. 核心演示场景

营销运营准备发起“东南亚暑期旅行节”，目标市场为中国、新加坡和澳大利亚。

系统完成以下流程：

1. 分析历史活动和当前库存。
2. 识别曼谷高星酒店、新加坡亲子酒店及上海—普吉航线存在供给缺口。
3. 创建 Hotel、Flight 两条产线的招商任务。
4. 根据产线和市场自动分配负责人。
5. 供应商提交商品后，系统验证价格、库存、日期和折扣等信息。
6. 商品进入货品池，并按照对应产线模型进行评级。
7. 系统输出评级分数、置信度和主要影响因素。
8. 高分商品进入“建议上架”，低分商品获得可执行的改进建议。
9. 系统发现曼谷酒店供给过度集中于某一供应商，自动触发风险预警。
10. 活动结束后，系统生成供应商表现和产线招商策略复盘报告。

该场景将作为 MVP 数据准备、功能验收和演示视频的统一主线。

## 6. 产品范围

### 6.1 招商活动管理

支持创建营销活动及其招商需求。

活动主要字段：

- 活动名称与活动描述
- 目标市场和目标客群
- 活动时间与招商截止时间
- 招商产线范围
- 商品数及库存目标
- 预算、折扣和价格竞争力目标
- 招商负责人及协作者

主要功能：

- 创建、编辑、复制和归档招商活动
- 将活动需求自动拆解为产线招商任务
- 按产线、区域和负责人自动分发任务
- 展示招商完成率、商品准备率和剩余时间
- 生成截止提醒、逾期和供给不足预警

### 6.2 AI 招商需求结构化

用户可以输入自然语言需求，例如：

> 为东南亚暑期活动招募曼谷和普吉岛酒店，重点关注四星以上、暑期有房、价格低于主流平台 5% 以上的亲子酒店。

AI 将需求转换为结构化条件：

```json
{
  "product_line": "hotel",
  "destinations": ["Bangkok", "Phuket"],
  "star_rating_min": 4,
  "travel_period": ["2026-07-01", "2026-08-31"],
  "inventory_required": true,
  "competitor_price_advantage": 0.05,
  "target_segments": ["family"]
}
```

用户确认后，系统生成招商任务和对应筛选规则。AI 需要标注无法确定的字段，不得以猜测值直接创建任务。

### 6.3 商品提交与自动校验

供应商或招商人员可以通过 CSV/Excel 导入、模拟 API 或手工录入提交商品。

系统自动完成：

- 数据格式和必填字段校验
- 重复商品检测
- 日期范围与活动周期校验
- 价格、库存和折扣异常检测
- 商品与当前活动招商条件的适配性判断
- 商品和供应商基础状态检查

校验结果分为：

- 通过
- 需要补充信息
- 不符合入池标准
- 疑似异常，等待人工审核

### 6.4 货品池管理

商品主流程状态如下：

```text
招商中 → 已提交 → 待校验 → 待评级 → 评级中
       → 待审核 → 待上架 → 已上架
```

异常状态包括：

- 信息待补充
- 评级失败
- 已驳回
- 已过期
- 已下架

货品池支持按活动、产线、市场、供应商、商品等级、状态、价格竞争力、库存健康度和风险标签进行筛选。

每次状态变更必须记录触发来源、操作者、变更时间和原因。

### 6.5 产品评级与排序引擎

评级引擎采用“硬性规则过滤 + 指标标准化 + 加权评分 + 置信度”的方式，使评分结果可解释、可配置和可复现。

#### Hotel 初始评分模型

| 维度 | 初始权重 |
|---|---:|
| 价格竞争力 | 30% |
| 历史销量与转化率 | 20% |
| 房态与库存稳定性 | 20% |
| 评分及服务质量 | 15% |
| 目标客群匹配度 | 10% |
| 供应商质量 | 5% |

#### Flight 初始评分模型

| 维度 | 初始权重 |
|---|---:|
| 航线覆盖价值 | 25% |
| 折扣深度 | 25% |
| 可售库存 | 20% |
| 出行时效与航班时间 | 15% |
| 历史转化表现 | 10% |
| 供应商质量 | 5% |

评分输出包括：

- 综合评分：0～100
- 产品等级：S / A / B / C
- 模型版本与置信度
- 各维度得分及权重
- 主要加分项和风险项
- 可执行的商品改进建议
- 是否建议上架
- 前台推荐和排序建议

示例输出：

> 曼谷河畔酒店，评级 A，综合分 86，置信度 0.91。价格较竞品低 8%，库存稳定且历史转化较高；主要风险是供应商取消率偏高。建议进入活动主会场，但不进入前三推荐位。

### 6.6 Product Line Intelligence Agent

Agent 是项目的核心差异化能力。用户可以询问：

- 哪些市场存在明显供给缺口？
- 本次活动应该优先招商哪些商品？
- 哪些商品值得优先上架？
- 哪些供应商存在集中度风险？
- 为什么酒店产线的货盘健康度下降？
- 如果活动目标提升 20%，还需要补充多少库存？

Agent 调用受控的内部分析工具，输出：

- 结论
- 数据依据和统计口径
- 风险与限制
- 推荐行动
- 回答置信度
- 可供用户确认创建的招商任务

Agent 默认只读。创建任务、调整评分权重、变更商品状态等操作必须展示变更预览，并在用户确认后执行。

### 6.7 供给缺口与集中度分析

系统按照市场、城市/航线、产品类型、价格带、客群、出行日期和供应商计算供给覆盖。

主要指标包括：

- 目标商品数与当前商品数
- 目标库存与当前库存
- 供给覆盖率和缺口数量
- 供应商集中度
- 高评级商品占比
- 即将过期商品比例

供应商集中度将使用 HHI 等指标，避免只展示简单占比。系统需要同时显示指标解释、计算范围和风险阈值。

### 6.8 货盘健康度

货盘健康度范围为 0～100，初始模型如下：

| 维度 | 初始权重 |
|---|---:|
| 供给目标完成度 | 25% |
| 高评级商品占比 | 20% |
| 库存稳定性 | 15% |
| 价格竞争力 | 15% |
| 供应商多样性 | 15% |
| 商品新鲜度 | 10% |

系统需要展示总分、历史趋势、维度分数和主要扣分原因，不展示无法解释的单一数字。

### 6.9 自动化规则中心

系统支持事件驱动的自动化规则，例如：

```text
当某市场供给覆盖率低于 70%
且距离招商截止时间少于 5 天
则：
1. 创建高优先级缺口预警
2. 通知产线负责人
3. 由 Agent 生成补充招商建议
```

其他规则包括：

- 竞品价格下降超过阈值时重新评级
- 库存连续下降时触发补货提醒
- 商品数据过期时暂停推荐
- 供应商取消率异常时降低供应商质量分
- 招商截止前自动发送分级提醒

所有规则必须支持启停、版本记录、最近执行结果和失败重试状态查询。

### 6.10 产线与供应商复盘

活动结束后，系统生成：

- 招商目标达成率
- 各市场供给缺口变化
- 各等级商品转化表现
- 评分与实际表现的相关性
- 供应商履约率、取消率和转化表现
- 招商周期与逾期情况
- 高分但低转化商品清单
- 下一次招商策略建议

系统还需要提供跨活动趋势分析，形成长期供应商画像和独立于单次活动的产线周期报告。

## 8. MVP 边界

### 8.1 必须实现

- Hotel、Flight 两条产线
- 一条完整的招商状态流
- CSV 批量导入和数据校验
- 基于配置的自动入池规则
- 两套可解释评分模型
- 评级、置信度与特征贡献展示
- 活动、货品池和商品详情页面
- 供给缺口与供应商集中度分析
- AI Agent 数据问答及策略建议
- 3～5 条自动化预警规则
- 可复现的模拟数据集
- Docker 一键启动

### 8.2 暂不实现

- 真实全球供应商系统接入
- 真实竞品大规模爬虫
- 在线机器学习训练平台
- 完整企业级权限审批体系
- 真正控制生产环境的前台推荐系统
- 多租户和企业级计费

项目可以使用公开数据与模拟数据演示业务闭环，但需要清楚标明数据来源和模拟规则。

## 9. 关键业务规则

1. 商品必须先通过产线硬性入池规则，才进入评分阶段。
2. 同一商品可以参与多个活动，但每个活动拥有独立的货品池状态和评级快照。
3. 评分模型必须记录产线、版本、权重、计算时间和输入数据版本。
4. 商品关键字段更新后，原评级失效并进入重新评级队列。
5. Agent 不得绕过权限和人工确认直接修改核心业务数据。
6. 置信度不足时，系统必须展示数据缺口，不得输出伪确定结论。
7. 自动化执行失败时，系统保留失败记录并向负责人发出通知。

## 10. 非功能需求

- 每个评分结果必须可解释。
- Agent 回答必须展示数据来源、统计口径和计算时间。
- 所有自动状态变更保留审计日志。
- 评分模型和自动化规则可配置、可版本化。
- 关键操作支持人工确认，必要时支持回滚。
- 数据不足时降低置信度并说明缺失项。
- 常用仪表盘查询响应时间目标为 2 秒以内。
- 异步评级和批量导入需要展示进度及失败原因。
- MVP 默认中文界面，数据模型和代码命名使用英文；国际化作为加分项。

## 11. 建议技术架构

```text
Frontend
Next.js + TypeScript + Tailwind CSS + ECharts

Backend API
FastAPI 或 NestJS

Workflow
Celery / BullMQ + 定时任务 + 事件驱动规则

Database
PostgreSQL

AI Layer
LLM Tool Calling + 受控分析工具 + 可选 RAG

Analytics
Polars / Pandas + SQL

Delivery
Docker Compose + GitHub Actions
```

初步服务边界：

- Campaign Service：活动和招商任务
- Product Pool Service：商品及其生命周期
- Grading Engine：评级和置信度计算
- Intelligence Service：缺口、集中度和健康度分析
- Automation Engine：规则管理及事件处理
- Agent Service：自然语言分析与策略建议
- Notification Service：站内通知和邮件模拟

最终模块边界和技术选型将在系统架构文档中确认。

## 12. 核心数据实体

- `Campaign`：营销活动
- `SourcingRequest`：招商请求
- `SourcingTask`：招商任务
- `Product`：标准商品
- `ProductSnapshot`：商品价格与库存快照
- `ProductPoolEntry`：商品在活动货品池中的状态
- `GradingResult`：评级结果
- `ScoringModel`：评分模型及版本
- `Supplier`：供应商
- `SupplierPerformance`：供应商长期表现
- `SupplyTarget`：市场及活动供给目标
- `AutomationRule`：自动化规则
- `Alert`：业务预警
- `AuditLog`：操作与状态变更记录
- `AgentRecommendation`：Agent 策略建议及确认状态

详细字段将在数据字典中定义。

## 14. 验收标准

MVP 达到以下条件时视为完成：

1. 用户可以从活动创建开始，完整演示商品进入已上架状态的主流程。
2. Hotel 和 Flight 商品能够使用不同规则及权重完成评级。
3. 任一评级结果都能追溯输入数据、模型版本和各维度贡献。
4. 仪表盘能够识别演示数据中的预设供给缺口和集中度风险。
5. Agent 能够基于系统真实查询结果回答核心演示问题，且不编造不存在的数据。
6. 自动化规则可以在预设条件下触发通知或重评任务。
7. 活动结束后能够生成包含供应商和产线指标的复盘结果。
8. 新用户可以按照 README 使用 Docker 在本地启动系统并载入演示数据。

## 17. 项目差异化

SupplyPilot AI 的竞争力不在于“为数据套一个聊天机器人”，而在于把 AI 放进招商、校验、评级、预警、建议和复盘的完整业务流程，并保留可解释性、人工确认、版本管理和审计能力。
