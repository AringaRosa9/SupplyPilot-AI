# SupplyPilot AI MVP 开发计划

> 状态：Active（M0 completed）
> 制定日期：2026-08-11
> 产品基线：[PRD](PRD.md)
> 界面基线：[前端页面与布局方案](frontend-design.md)

## 1. 开发目标

MVP 的首要目标不是一次性完成所有后台模块，而是交付一条可以真实运行、可解释、可演示的端到端业务链路：

```text
创建招商活动
→ AI 结构化活动要求
→ 自动拆解 Hotel / Flight 招商任务
→ 导入并校验商品
→ 商品进入货品池
→ 按产线完成评级
→ 人工审核并建议上架
→ 发现供给缺口和供应商风险
→ Agent 生成行动预览
→ 用户确认创建任务
→ 输出活动复盘
```

开发顺序遵循三个原则：

1. 先建立数据模型和业务状态机，再实现页面。
2. 先跑通确定性的业务逻辑，再接入 LLM 和自动化。
3. 每个阶段都必须形成可演示、可测试的纵向切片，避免前后端长期分离开发。

## 2. 建议技术基线

| 层级 | 建议选择 | 原因 |
|---|---|---|
| Web | Next.js + TypeScript + Tailwind CSS | 适合数据工作台、路由和服务端数据加载；与已确认的前端方向一致 |
| UI 基础 | Radix UI primitives + 自定义组件 | 保留无障碍能力，同时避免套用通用后台模板 |
| 图表 | ECharts | 支持矩阵、趋势、贡献分析和复杂交互 |
| API | FastAPI + Pydantic | 与评分、数据分析和 Agent 工具共享 Python 生态 |
| ORM / Migration | SQLAlchemy 2 + Alembic | 明确模型、事务和版本迁移 |
| Database | PostgreSQL | 承载业务实体、JSON 配置、审计和分析查询 |
| Async / Cache | Redis + Celery | 承载批量校验、评级、规则执行和失败重试 |
| Analytics | SQL + Polars | 优先使用可追溯 SQL，复杂批处理使用 Polars |
| AI | LLM Tool Calling + 受控内部工具 | Agent 默认只读，写操作经过预览和确认 |
| Testing | Pytest + Vitest + Playwright | 覆盖业务逻辑、组件和演示主链路 |
| Delivery | Docker Compose + GitHub Actions | 保证一键启动与可复现演示 |

在 M0 结束前完成最终技术选型记录；如果 Redis/Celery 对 MVP 过重，可先以数据库任务表和进程内 worker 实现相同接口，但不能把异步逻辑直接耦合在 HTTP 请求中。

## 3. 实施阶段总览

| 阶段 | 核心结果 | 相对工作量 | 前置依赖 |
|---|---|---:|---|
| M0 设计固化与工程骨架 | 数据、状态、API 和项目结构可执行 | M | 无 |
| M1 演示数据与产品壳层 | 真实模拟数据驱动驾驶舱 | M | M0 |
| M2 招商业务闭环 | 活动、任务、导入、校验、货品池跑通 | XL | M1 |
| M3 评级与审核 | Hotel / Flight 可解释评级跑通 | L | M2 |
| M4 供给洞察与预警 | 缺口、健康度、HHI 和风险联动 | L | M3 |
| M5 Agent 与自动化 | 受控问答、行动确认和规则执行 | XL | M4 |
| M6 复盘与交付 | 复盘、质量、Docker 和演示材料完成 | L | M5 |

相对工作量只用于排序：S 为单一小任务，M 为一个完整纵向切片，L/XL 需要进一步拆成多个 Issue，不代表固定日历时间。

## 4. 分阶段开发内容

## M0：设计固化与工程骨架

> 完成状态：Done（2026-08-11）。架构、数据、评分与 Agent 契约已固化；Web/API/Worker/PostgreSQL/Redis 工程骨架、迁移、健康检查、Docker Compose 与 CI 已建立。

### 产品与数据

- 完成核心实体关系和数据字典：Campaign、SourcingTask、Product、ProductPoolEntry、GradingResult、Supplier、SupplyTarget、Alert、AuditLog、AgentRecommendation。
- 固化货品池主状态机和异常状态，明确每次迁移的触发者、前置条件和审计内容。
- 固化 Hotel / Flight 硬性入池规则、评分输入和缺失数据策略。
- 定义核心指标口径：覆盖率、库存缺口、高评级占比、HHI、货盘健康度。
- 定义 Agent 工具协议和写操作确认协议。

### 工程

- 初始化 `frontend`、`backend`、数据库迁移和 Docker Compose。
- 建立环境变量示例、日志格式、错误响应规范和 API 版本路径。
- 建立基础 CI：格式检查、类型检查、单元测试、构建检查。
- 增加 `/health`、数据库连接检查和前端环境检查。

### 前端

- 将已确认 HTML 原型拆成应用壳层：导航、顶部上下文栏、页面容器、Agent Rail。
- 建立颜色、排版、间距、状态和图表语义 token。
- 建立基础组件：Button、Tag、FilterChip、DataTable、EmptyState、ErrorState、Drawer、Toast。

### 退出条件

- `docker compose up` 能启动 Web、API、PostgreSQL 和任务执行组件。
- Web 能访问 API 健康检查。
- 数据实体、状态机、指标和 Agent 边界均有文档，不再依靠口头约定。
- CI 能阻止类型错误、格式错误和失败测试进入主分支。

## M1：演示数据与产品壳层

### 模拟数据

- 生成统一演示活动“东南亚暑期旅行节”。
- 覆盖中国、新加坡、澳大利亚市场以及 Bangkok、Phuket、Singapore、Chiang Mai 等目的地。
- 准备 Hotel / Flight 商品、供应商、库存快照、价格、历史转化和履约表现。
- 固定植入可验证异常：曼谷供应商集中、上海—普吉库存不足、亲子酒店缺口、12 个商品待审核。
- 使用固定随机种子，保证每次初始化后的指标和截图一致。

### 后端

- 建立 seed 命令和演示数据重置能力。
- 实现驾驶舱聚合查询：待决策事项、货盘健康度、活动准备度、市场覆盖矩阵。
- 实现轻量演示角色和权限上下文，不建设完整企业 IAM。

### 前端

- 完成登录/演示角色进入页。
- 完成全局导航、活动上下文、通知入口和角色切换。
- 将驾驶舱原型连接真实 API，不在组件中保留硬编码业务数据。
- 完成加载、空数据、查询失败和数据更新时间展示。

### 退出条件

- 重置演示数据后，驾驶舱稳定显示 PRD 中约定的缺口和集中度风险。
- 切换角色会改变默认视图和可见操作。
- 常用驾驶舱查询在本地演示环境中目标响应时间不超过 2 秒。

## M2：招商业务闭环

### M2.1 活动与任务

- Campaign 创建、编辑、复制、归档和列表筛选。
- 活动详情页：概览、任务、活动货品、风险、复盘占位。
- SourcingTask 创建、负责人分配、截止时间、优先级和完成度。
- 按产线、区域和负责人执行可配置的任务分配规则。
- 所有关键变更写入 AuditLog。

### M2.2 AI 需求结构化

- 建立自然语言输入和结构化字段 Schema。
- 第一版可使用 LLM，但必须通过 Schema 校验，并显式返回 `uncertain_fields`。
- 用户逐字段确认后才能创建活动和任务。
- 保存原始输入、模型输出、用户修订和最终确认值。
- LLM 不可用时允许用户完全手工填写，不阻塞主流程。

### M2.3 商品导入与校验

- CSV 上传、模板下载、字段映射和导入批次记录。
- 校验必填字段、格式、重复商品、日期、价格、库存、折扣和活动适配性。
- 问题按阻塞、需补充和疑似异常分类，并定位到行与字段。
- 支持仅提交通过项、下载失败明细和重新导入。
- 大批量校验进入异步任务，前端展示进度和失败原因。

### M2.4 货品池状态流

- Product 与活动级 ProductPoolEntry 分离。
- 实现主状态与异常状态迁移规则。
- 商品关键字段变化后，使旧评级失效并进入重新评级队列。
- 完成全局货品池表格、保存视图、批量操作和快速详情侧栏。

### 退出条件

- 用户可以从创建活动开始，将 CSV 商品导入并推进到“待评级”。
- 同一商品可进入多个活动，活动状态和评级快照相互独立。
- 非法状态迁移会被 API 拒绝，并留下可理解的错误信息。
- 导入失败可定位、可下载、可重试，不出现静默丢数据。

## M3：评级与人工审核

### 评分引擎

- 实现“硬性规则过滤 → 标准化 → 加权评分 → 等级映射 → 置信度”流水线。
- 分别实现 Hotel 和 Flight 初始模型。
- 模型配置包含产线、版本、权重、阈值、生效时间和状态。
- 每次评分记录输入快照、模型版本、维度得分、权重、贡献和计算时间。
- 缺失数据影响置信度，并生成明确的数据补充建议。

### 后端与异步任务

- 支持单商品评分、批量评分、重评和任务失败重试。
- 评分执行具备幂等性，重复消息不生成冲突结果。
- 保留历史评分，当前评分通过明确引用指向最新有效结果。

### 前端

- 货品池展示评级、分数、置信度和风险标签。
- 完成评级详情页：贡献条、基准比较、原始证据、改进建议和审计时间线。
- 完成建议上架、要求补充、驳回和批量审核。
- 低置信度结果必须优先展示缺失项，而不是只展示分数。

### 测试

- 为各维度边界、硬规则、缺失数据和等级阈值建立参数化测试。
- 使用固定样本建立评分金丝雀测试，防止权重或公式变动导致无意漂移。

### 退出条件

- Hotel 和 Flight 使用不同模型完成评分。
- 任一分数都能追溯到输入数据、模型版本和维度贡献。
- 更新关键字段后旧评级自动失效，重新评级后保留历史记录。
- 演示样本的等级和解释与评分文档一致。

## M4：供给洞察与预警

### 分析能力

- 按活动、市场、城市/航线、产线、价格带、客群和日期计算供给覆盖。
- 实现目标商品数、目标库存、当前供给、缺口、高评级占比和即将过期比例。
- 实现供应商份额、Top N 占比和 HHI，保存阈值和统计范围。
- 实现货盘健康度总分、六个维度、趋势和主要扣分原因。

### 前端

- 完成供给缺口矩阵、缺口优先级、趋势和关联任务。
- 完成货盘健康度分解和 Hotel / Flight 对比。
- 完成供应商表现矩阵及跨活动供应商详情。
- 所有图表显示统计口径、范围、更新时间，并能下钻到业务实体。

### 预警

- 生成供给不足、临期、集中度、库存下降和商品过期预警。
- 驾驶舱决策队列与通知中心读取同一预警数据源。
- 支持预警认领、处理、忽略和处理说明。

### 退出条件

- 系统能够稳定识别演示数据中的曼谷集中度和上海—普吉库存缺口。
- 任何风险均可从汇总指标下钻到具体活动、商品或供应商。
- 健康度不是单一黑盒数字，所有扣分均能解释。

## M5：Intelligence Agent 与自动化

### Agent 工具

- 供给缺口查询。
- 商品评级解释与优先上架分析。
- 供应商集中度与表现查询。
- 货盘健康度变化归因。
- 活动目标情景测算。
- 招商任务草案生成。

### Agent 协议

- 回答固定包含：结论、数据依据、统计口径、风险与限制、推荐行动、置信度。
- 每次工具调用记录参数、结果摘要、耗时和错误，不记录密钥或敏感 Prompt。
- 工具只接受受控参数，不允许执行任意 SQL。
- 创建任务、调整评分权重和状态变更必须生成 AgentRecommendation。
- 用户确认时校验推荐是否过期，并记录确认者与最终差异。

### Agent 前端

- 实现上下文 Intelligence Rail 和完整 Agent 工作台。
- 当前活动、商品、筛选条件和时间范围可见、可移除。
- 数据依据可以跳回对应页面并恢复筛选范围。
- 行动预览清晰展示将创建或修改的实体，确认后反馈执行结果。

### 自动化规则

- 实现事件、条件、动作、版本、启停、执行记录和失败重试。
- MVP 提供 3–5 条预置规则：覆盖率临期预警、价格变化重评、库存下降提醒、商品过期暂停、供应商取消率异常。
- 规则编辑采用结构化表单和自然语言摘要，不实现自由拖拽编排器。
- 支持使用演示数据模拟命中范围，再启用新版本。

### 安全与评估

- 建立核心问题集、数据缺失问题、越权请求和 Prompt Injection 测试集。
- 校验回答中的关键数字必须来自工具返回，不允许模型自行计算或补造。
- 工具或模型失败时降级到确定性报表和人工操作。

### 退出条件

- Agent 能回答 PRD 中的核心问题，并提供可验证的数据依据。
- Agent 不能绕过确认直接修改核心业务数据。
- 自动化规则可启停、可追踪、可重试，失败会生成通知。
- 预设评估集通过率达到项目确定的门槛后才进入演示主线。

## M6：复盘、质量与交付

### 复盘

- 生成活动目标达成率、缺口变化、等级转化、供应商表现和招商周期分析。
- 对比评分与实际表现，列出高分低转化商品。
- 生成下一次招商策略建议，并明确数据局限。
- 支持浏览器打印为 PDF；MVP 暂不建设复杂报表设计器。

### 质量

- 完成核心页面键盘操作、焦点、对比度和屏幕阅读器基础检查。
- 校验 1280px、1440px 桌面布局和主要平板断点。
- 优化驾驶舱与货品池查询，补充数据库索引和慢查询记录。
- 完成错误边界、空状态、异步超时、重试和离线提示。
- 对核心 API、评分任务和 Agent 工具增加结构化日志与关键指标。

### 交付

- 完成 Docker 一键启动、数据库迁移和演示数据初始化。
- 完成 README 启动说明、系统架构、数据字典、评分和 Agent 文档。
- 完成 3–5 分钟演示脚本、截图、GIF 或视频。
- 明确模拟数据、已知限制、非生产能力和未来路线。

### 退出条件

- 新环境按照 README 可以一次启动并载入演示数据。
- Playwright 主链路测试可以完整执行演示流程。
- PRD 的 8 项 MVP 验收标准均有对应测试或人工验收记录。
- 项目截图、演示视频与实际运行版本一致。

## 6. 测试策略

### 单元测试

- 状态迁移、导入校验、评分公式、置信度、HHI、健康度和规则条件。
- 前端格式化、筛选参数、权限判断和复杂交互组件。

### 集成测试

- CSV 导入到入池。
- 商品更新到重新评级。
- 活动目标变化到缺口重算。
- 事件触发到规则执行、通知和审计。
- Agent 推荐到用户确认和任务创建。

### 端到端测试

至少维护两条 Playwright 流程：

1. 完整演示主链路。
2. 异常链路：导入失败、低置信度、规则执行失败和 Agent 写操作未确认。

### 数据与模型回归

- seed 数据使用固定版本和校验摘要。
- 评分模型变更必须更新版本并运行金丝雀样本。
- 指标 SQL 使用固定样本验证口径。
- Agent 使用离线问题集记录正确性、依据完整度和越权率。

## 7. Definition of Done

任一功能只有同时满足以下条件才视为完成：

- 用户流程和异常流程均可操作。
- API 输入输出有 Schema，错误信息可理解。
- 核心业务变更有审计记录。
- 加载、空数据、失败、无权限状态齐全。
- 必要的单元或集成测试通过。
- 文档、模拟数据和页面口径同步更新。
- 不引入无法解释的评分、指标或 Agent 结论。
- 在支持的桌面断点完成基本视觉检查。

## 8. 首轮 Issue 拆分建议

开发启动时优先建立以下 Issue：

1. `chore: scaffold web api database and docker compose`
2. `docs: define entity model and product pool state machine`
3. `docs: define hotel and flight scoring contracts`
4. `feat(data): create deterministic SEA summer campaign seed dataset`
5. `feat(web): implement app shell and design tokens from approved prototype`
6. `feat(api): expose dashboard aggregation endpoints`
7. `feat(web): connect dashboard to seeded API data`
8. `test: add CI checks and first dashboard smoke test`

前 8 个 Issue 完成后，再开始 M2 的活动与商品导入功能。这样可以尽早获得一个使用真实数据、能够持续验证的产品骨架。

## 9. 范围控制

以下内容不进入 MVP 主计划：

- 真实供应商和生产库存系统接入。
- 大规模竞品爬虫。
- 完整企业 IAM、审批流和多租户。
- 在线模型训练平台。
- 可自由拖拽的仪表盘或自动化编排器。
- 移动端完整编辑能力。
- 直接控制生产前台排序或执行不可逆业务决策。

新增需求如果会影响演示主链路、数据模型或 M2–M5 顺序，应先更新 PRD 和本计划，再进入开发。
